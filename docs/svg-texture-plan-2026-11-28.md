# 底图支持 SVG：规划稿（2026-11-28）

> 状态：**已拍板，P0 落码中**。五个决策见 §9 末尾的「拍板结果」。
> 本文所有结论都带取证位置；数字来自本机实测（dash 素材 / 3200×2000 生成件 / 现行门禁）。

## 0. 一页结论

1. **值得做，但不应该"全面替换位图"**。做成第二条素材通道（`vector`），与位图并存，生成时提问选哪个。
2. 内置 24 张里可以先拿 **dash（琥珀）** 做试点——它的图样本来就是纯几何（同心圆角矩形 + 同心圆），天生属于矢量。
3. 真正的难点不是"能不能渲染"，而是三件容易被低估的事：
   - 白名单是**四处硬编码**，漏一处就是"静默丢弃"（今天传 `.svg` 就是这种下场）；
   - 归一化会把矢量**重编码回位图**（3200 内核裁剪 + PNG 重存），矢量优势当场归零，且没有任何报错；
   - 门禁契约对矢量的判据**不成立**（"素材宽 ≥ 1600"、"sha256 + 逐像素合成"），需要单独的 vector 分支。
4. 建议分期：P0 = 能收、能渲染、有安全校验；P1 = 生成时提问；P2 = 内置 dash 试点；P3 = 颗粒与 LLM 直产的取舍。

## 1. 现状取证：今天传 SVG 会发生什么

`.svg` 会在**四处**被拦下，而且都是"静默"的：

| # | 位置 | 行为 | 后果 |
| --- | --- | --- | --- |
| 1 | `theme-tool.js` `sniffImage()` | 只认 JPEG/PNG/WebP 魔数，SVG 是文本 → 返回 `''` | `stashTexture` 返回 null，**整张被丢弃** |
| 2 | `index.js` `/api/texture` 端点 | 文件名正则 `^[a-f0-9]{16}\.(jpg\|png\|webp)$` + content-type 映射 | 就算落了盘也 400 |
| 3 | `src/25-chat-card.js` 与 `client.js`（同源镜像） | 客户端也有一份同样的白名单 | 前端取不到 |
| 4 | 工具描述文本 | "JPEG/PNG/WebP, <=3 MiB" | 模型根本不会去产 SVG |

**陷阱（比白名单更隐蔽）**：`zrTexNormalizeUrl()` 走 `drawImage → getImageData → toDataURL('image/png')`。
一张**带不透明底**的 SVG 会被这条链降级成 3200 内的位图，之后 `verify:texture` 再拿它当位图量——
矢量的分辨率优势全部消失，而界面一个字都不会提示。这与 R-11 那个"1000 宽被放大成色斑"是同一类事故：
**规则在替用户做他没要求的决定，且不告诉他。**

## 2. 为什么这套底纹天然适合矢量（实测）

拆开 dash 的内置素材看（`assets/bg/bg-dash.webp` / `bg-soft-dash.webp`）：

| 指标 | 深色 | 浅色 | 说明 |
| --- | --- | --- | --- |
| 尺寸 | 1600×1000 | 1600×1000 | 与 SVG `viewBox` 同尺度 |
| 不透明像素占比 | 1.92% | 1.91% | 98% 是透明——本质是"线"不是"图" |
| 最大 alpha | 45/255 | 45/255 | 0.6.44 那次 alpha 归一后的值 |
| 墨色 | `#b89a74`（暖琥珀） | `#987c59` | 深色亮于底、浅色暗于底 |
| 文件 | 3.1 KB | 3.1 KB | 手绘 SVG 原型：**1.1 KB** |

也就是说：内置素材本来就不是"照片"，而是**几根线**。用位图存几根线，代价是
① 换分辨率就得重出图；② `cover` 放大后线条发虚（见第 6 节的 4× 对照）；③ 每条线要存 1600×1000 的画布。

而合成路径对"线"是最简单的一档：内置素材 `bgIsImage=false`，走**普通 alpha 合成**，
`a·b+(1-a)·b` 在透明处恒等于底色。R-12/R-13 那两轮反复（multiply 蒙灰、极性翻转）
**全都只发生在"满幅位图"这条路上**——矢量透明线稿根本没有这些特例。

## 3. 方案：`vector` 作为独立素材通道

### 3.1 数据形状（尽量不动现有结构）

- `texture` 记录照旧是 `{ name, mime, bytes }`，只是 `mime` 可能是 `image/svg+xml`、扩展名 `.svg`。
- `bg.kind` 仍是 `texture`（合成规则、透明度、遮罩全部复用）。
- **不新增持久字段**：判定"是不是矢量"只看 `mime`/扩展名，读完即用。

### 3.2 归一化：矢量**跳过**像素重写

| 素材 | 现在的处理 | 矢量通道的处理 |
| --- | --- | --- |
| 位图 | 采样底色 → 极性翻转 → 余量压缩 → 可能重编码 | 不变 |
| SVG | 会被重编码成 PNG（陷阱） | **跳过**，改为静态校验（见 3.3），解析失败才回落原值 |

为什么可以跳过对齐：矢量素材由生成方/作者直接给出 `stroke` 颜色，把"底色对齐"交给**生成约束**
（浅色用暗墨 `#987c59`、深色用亮墨 `#b89a74`）比事后逐像素改更可靠，也不会把文件变成位图。

### 3.3 安全校验（在服务端落盘前做，执行期强制）

拒绝而不是"尽力清洗"——半坏的素材比没有素材更难查：

1. 必须是 `<svg` 根元素，且有 `viewBox`（或 `width`+`height`）；
2. 出现 `<script`、`<foreignObject`、`on\w+\s*=`、`javascript:`、外部 `href`（`http`/`//`）→ 拒；
3. **滤镜白名单**：允许 `feGaussianBlur`/`feTurbulence` 之外的都不放行，或干脆 P0 阶段一律拒 `filter=`
   （理由见 5.1）；
4. 大小上限：**64 KiB**（1.1 KB 的原型离上限很远；这个数字是防"手写 SVG 里塞了 base64 位图"）。

### 3.4 安全不变量（写进 README，和现有承诺并列）

> SVG **只允许经 CSS `url()` 或 `<img>` 使用**，永远不内联进 DOM。

理由：SVG 作为**图片**加载时处于 secure static mode——脚本不执行、外部资源不加载。
一旦内联进 DOM，它就是一个完整的脚本面。这条不变量比任何清洗都可靠，必须写死。
（现有链路正好满足：`/api/texture` 回传字节 → FileReader → `data:` URL → CSS `url()`。）

### 3.5 生成侧：先问，再选

工具新增 `textureMode: 'vector' | 'raster' | 'ask'`，`ask` 时**必须先问用户**（与 R-13 同一个教训：
靠描述约束模型等于没约束）。建议的提问措辞：

> 底纹要哪一种？
> - **矢量线稿**：任意分辨率都清晰、几 KB、颜色可钉死；适合极简/几何/细线。
> - **位图质感**：有纸纹、颗粒、手绘笔触；适合暖纸、做旧、水彩那类。

两种各自的真实优势（写进工具描述，避免模型一刀切推荐 SVG）：

| | 矢量 SVG | 位图 |
| --- | --- | --- |
| 分辨率 | 任意 DPI 都锐（内置 dash 在 DPR2 已经是插值放大的） | 超过原生分辨率就发虚 |
| 体积 | 1–10 KB（几根线） | 100 KB–2 MB |
| 颜色 | 可以直接把墨色写成某个色值 | 靠模型猜，实测偏 5–10 级 |
| 颗粒 / 纸纹 | 弱：`feTurbulence` 全屏光栅化贵，`pattern` 噪点偏机械 | 强项，也是它存在的理由 |
| 手绘感 | 弱：模型写的 SVG 容易"太几何" | 强项 |
| 可复现 | 同一份 SVG 永远一样 | 每次重出都不一样 |

## 5. 风险与取舍

1. **全屏滤镜的代价**：`feTurbulence` 铺满窗口时，每次缩放/重排都要重新光栅化，实测上会掉帧。
   这条决定 P0 不收 `filter`。想要颗粒就走"矢量线稿 + 64×64 噪点 pattern"（见 5.4）。
2. **data URL 体积**：base64 后 +33%，1.1 KB → 1.5 KB，可忽略；但要在 64 KiB 上限里预留。
3. **浏览器对 svg-as-image 的限制**：无脚本、无外链——正好是我们要的，反过来也是限制
   （不能引用外部字体/图片，字体必须转路径）。
4. **颗粒怎么办**：可选方案是把颗粒做成 `<pattern>` 里的一张小噪点，
   或继续用位图承载颗粒（那就回到"混合素材"：SVG 线 + 位图颗粒两层）。
   这条路要不要走，见第 8 节第 4 问。
5. **兼容**：已应用的主题 `kind` 不变、IDB 里的 data URL 不变，不受影响。

## 6. 原型（已落盘，可现场打开）

`docs/svg-texture/`：

- `dash-dark.svg` / `dash-light.svg`：按内置 dash 的**图样与统计**手绘的近似矢量（1.1 KB / 张，
  `viewBox 1600×1000`，墨色与 alpha 对齐内置素材：`#b89a74` / `#987c59`，`stroke-opacity 0.176`）。
  **不是位图描摹**，是按"同心圆角矩形 + 同心圆"重新画的，用来验证这条路能不能成立。
- `demo.html`：同一套合成规则（`::before` + `inset:0` + `cover` + 0.595 不透明度 + 底部 320→60px 淡出），
  位图 vs SVG 并排，含"放大 4×"那一段。
- `demo-zoom.html`：只保留 4× 放大与不透明度拉满的对照，用于看清边缘质量。

实测对照（4× 放大、不透明度拉满）：位图那条线已经糊成 5–6px 宽的软带，SVG 仍是 1px 的干净边缘。
真实运行时（0.595、约 1px 线宽）两者肉眼差距会小很多，但**在高 DPI 与系统缩放下差距会重新出现**——
这正是 R-11 那次"模糊色斑"的同一条物理原因。

## 7. 验收标准

- 传 `.svg` 能出卡、明暗各一、渲染正确（不糊、不蒙灰）；
- 传带 `<script>` / 外链 / `<foreignObject>` / 无 `viewBox` / 超 64 KB 的 SVG → **被拒且原因可读**；
- 带不透明底 rect 的 SVG **不会**被悄悄降级成位图（要么保持矢量，要么报错）；
- `npm test` + `verify:all` 全绿；新增 `test-svg-texture.mjs` 含"该红必须红"的反向用例；
- dash 试点在 DPR 2 / 4× 下线条锐利（截图对照留档）。

## 8. 补充：SVG 能做动画吗（2026-11-28 实测）

**能**，两条机制都在：SVG 文档内的 SMIL（`<animate>` / `<animateTransform>`）与文档内 CSS 动画。
本机（DSH 桌面端同款 Chromium）实测：同一个带动画的 SVG，用 **CSS `background-image`** 与 **`<img src>`**
两条路都真的在动——420 ms 内圆点位移约 12 px，两条路改动的像素数完全相同（2068 px）。
所以「动画放进 background-image 会被冻成首帧」这条旧说法**在当前 Chromium 上不成立**
（换内核仍不保证，Safari/Firefox 历史上行为不一）。

但对**底纹**这个用途，动画要过四关，任何一关不过就不该默认开：

| 关 | 具体代价 |
| --- | --- |
| 合成链 | `::before` 上叠着 `opacity`、`mask-image`、深色还有 `mix-blend-mode: lighten`。动画层每帧都要重新混合+遮罩 → **全窗口重绘**，成本比静态图高一个量级 |
| 门禁语义 | 契约与归一化都是**单帧**语义（抽帧只能抽 t=0）。一旦收动画，`verify:texture` 量到的只是第一帧，必须写死"按第 0 帧判定"，否则数字会随动画漂 |
| 可访问性 | 文字背后持续运动，对长时间盯屏的人不友好；必须能被 `prefers-reduced-motion` 一刀关掉 |
| 功耗 | 装饰性底纹让 GPU 常驻唤醒；4K 下尤其明显。这与"若隐若现、不抢注意力"的设计目标也冲突 |

如果要"活一点"，按代价从低到高三个档：

1. **素材不动，动伪元素**（推荐第一选）：静态 SVG/位图 + 极慢的 `background-position` / `transform`
   （20 s 走 2%，或 12 s 呼吸一次 1%），肉眼几乎察觉不到在动，但不会"死死贴住"。
   零新增素材、零渲染风险，位图也能用。
2. **SVG 内 SMIL 只动少数元素**：例如一颗光点沿某条弧线走，`dur` 拉到 8–20 s。
   文件仍 1–2 KB；但必须在 `mask + mix-blend-mode` 下实测帧率，掉帧就退回第 1 档。
3. **canvas / WebGL**：不推荐。插件零依赖、要打包，收益不抵成本。

结论与建议：**P0 不做动画**，把"动作底纹"列成 P4 的独立开关（默认关，`prefers-reduced-motion` 强制关），
并且先在 dash 试点上量一次真实帧率再决定——量不出来就不写进默认值。

## 9. 拍板结果（2026-11-28）

| # | 问题 | 决定 | 对落码的约束 |
| --- | --- | --- | --- |
| 1 | 矢量只收纯线稿 SVG？ | **接受**：拒滤镜 / 外链 / 脚本 / ≤64 KiB | 校验器按"拒绝而不是清洗"写，且每条拒绝理由都要可读；必须有"该红必须红"的反向单测 |
| 2 | 内置是否换 SVG？ | **先 dash 试点**，看过观感再决定其余 | 换 dash 时契约要重测（sha256 变），`verify:texture` 先补 vector 分支 |
| 3 | 生成提问默认值？ | **按建议**：`ask` 且不预设；必须给默认时默认位图 | `textureMode: 'ask' \| 'vector' \| 'raster'`，缺省 `ask` |
| 4 | 颗粒进不进 SVG？ | **先不做**（留 P3） | P0 校验器直接拒 `filter` 与 `<image>`，不留半开状态 |
| 5 | 要不要动作底纹？ | **按建议**：P0 不做；只留第 1 档（伪元素极慢位移）作为 P4 独立开关 | 动画素材一律不收；第 1 档要能 `prefers-reduced-motion` 关闭 |

落码顺序（P0 → P1 → P2）：白名单与校验器 → 跳过归一化 → 生成提问 → dash 试点。
P0 完成判据：传合规 SVG 能出卡并正确渲染、传危险 SVG 被拒且原因可读、`npm test` 全绿。
