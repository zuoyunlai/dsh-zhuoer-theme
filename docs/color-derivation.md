# 调色口径：为什么用 OKLCH 表达「抬亮一点」

## 结论先说

**目标是对比度阈值，表达方式是 OKLCH 的 ΔL。** 两件事分开：

- **判据**（机器）：某套主题的文字在「最不利背景」上必须 ≥ 4.5:1。这条由 `verify:contrast` 与 `verify:texture` 硬判；
- **口径**（人）：为了达标让出的亮度，用 OKLCH 的 `ΔL` 记录，而不是「sRGB 加了 8 级」——后者在不同色相/饱和度上的感知步长不一样。

工具：`node scripts/oklch-step.mjs`（零依赖，sRGB ↔ OKLab 标准矩阵）。

```bash
node scripts/oklch-step.mjs --pair "#908072,#9b8d80"                    # 看两色在 OKLCH 里差多少
node scripts/oklch-step.mjs --lift "#908072" --dl 0.04 --base "#1a1210" # 抬 0.04 感知亮度 + 新旧对比度
node scripts/oklch-step.mjs --audit                                     # 复核 0.6.44 那 7 组
```

## 0.6.44 那 7 组到底差多少（实测）

为让底纹可见，暗色三级文字各抬了一次。用 OKLCH 复核：

| 主题 | 改动 | ΔL | ΔC | Δh° |
|---|---|---|---|---|
| dash | `#908072 → #9b8d80` | **0.0417** | -0.0032 | +1.80 |
| rose | `#86839c → #8e8ca3` | **0.0283** | -0.0034 | -1.36 |
| absolutely | `#85857f → #8a8a84` | 0.0167 | -0.0001 | -0.01 |
| crt | `#7c7c7c → #808080` | 0.0136 | 0.0000 | 0.00 |
| manuscript | `#918871 → #948c75` | 0.0124 | -0.0005 | +1.92 |
| knot | `#7a7a83 → #7d7d86` | 0.0102 | -0.0001 | +0.01 |
| miami | `#857ba3 → #887ea5` | 0.0096 | -0.0017 | +0.38 |

**ΔL 极差 0.0320（0.0096 ~ 0.0417，约 4.3 倍）**。这不是「手调得忽高忽低」，而是对比度约束的必然结果：
每套主题的起点余量不同——dash 的三级文字原来只比 AA 高 0.35，纹理一上来就破线，所以要让出最多；
miami 原本余量就够，只挪了一点。

所以判断标准是：**每套都恰好越过 4.5:1**（实测落在 4.55–4.62），而不是「ΔL 都等于某个值」。
硬要统一 ΔL，必然有一套过不了线。

## 以后怎么用

1. 调色前先算需要多少：`--lift <现色> --dl <猜>` 看对比度够不够，逐档逼近；
2. 定稿后把 `ΔL` 记进 CHANGELOG——下次有人问「为什么这套抬这么多」，答案是可复算的数，不是「看着调」；
3. 新增派生色（不是为对比度、而是为层级）时，反而应当**尽量等 ΔL**：那种场景手感一致性优先。
