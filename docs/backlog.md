# 待办（backlog）

按「动它的风险」排序，而不是按「看起来多重要」。每条都写清判据、影响面与验收方式，
免得下次打开时又要重新判断一遍该不该做。

## 1. `applyTokens` 剩余部分的拆分

**现状**：600 行（本轮之前 632 行）。已经从里面抽出 `applySurfaceFills`（27 行，纯函数，
只读 tokens、只写 tokens），剩下的部分几乎全是 DOM 与阴影 CSS 注入。

**为什么没继续**：剩余代码不是「长」，是「耦合」——它持有 `document`、`window.__zrSkinObs`
`MutationObserver`、`dispose` 闭包和一组运行时判断（宿主是否已有该节点、是否首次注入）。
把它切碎需要同时改生命周期，属于「改动面 = 全仓最难回归的一块」，
必须配真机回归（主题切换 × 11 套 × 明暗 × 自定义主题），不能混在发版里做。

**判据**：拆完之后 `client.js` 的行为必须逐 token 一致——可以用现有 `test-derive`
的快照对比 `overrideTokens` 收到的对象，而不是肉眼。

**验收**：`npm test` 全绿 + 11 套主题明暗切换无闪烁 + 自定义主题保存后即时生效。

## 2. `PANEL_CSS` 间距的全量重排

**现状**：本轮只做了两件事——字号收敛到 11/12/13/15/18/20（`11.5→12`），
间距收敛到 4px 网格（`gap 5→4 / 7→8`、`padding 7→8 / 9→8`、`padding-top 18→16`、
`radius 7→8`）。残留的 1/2/3px 是光学微调，**故意不动**。

**为什么不做全量**：0.4.1 那次回归（只缩放正文、其余不跟）就是「看起来应该没事」的改动
造成的。CSS 微调只能在真实界面里看，没有浏览器验证的前提下全量重排是赌博。

**判据**：先给面板做一张基线截图（设置页 + 编辑器抽屉 + JSON 弹层 × 明暗两套），
改完逐张对比；或引入视觉回归（`verify:visual`）后再动。

**验收**：截图 diff 为空或差异可解释。

## 3. 每个主题的对比度余量台账

**现状**：`verify:contrast` 只判「是否过线」，不记录「余量多少」。
某个主题可能刚好卡在 4.5:1，下次调色一碰就掉下去，而门禁到时才发现。

**判据**：把 11 套主题 × 明暗 × 关键前景/背景对的实测对比度存成一份台账，
门禁改为「不得比台账更低」，而不是「不得低于 4.5」。

**验收**：台账可由脚本再生，且故意把一个 token 调暗 1% 能让门禁变红。

## 4. 底图与字体的体积

**现状**：tarball 4.85 MB，其中字体 4.5 MB（23 个 woff2）、底图 21 张 webp。
字体是最大的那块，但中文字形子集化需要构建期依赖，会把「零构建」这个前提打破。

**判据**：先量一下 `assets/fonts` 里每个文件实际被用到多少字符——如果加载的只是
拉丁字母与少量标点，那 CJK 字形就是纯负担。

**验收**：tarball 降到 3 MB 以下且字体渲染无变化（截图对比）。
